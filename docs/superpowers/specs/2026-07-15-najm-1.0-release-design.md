# Najm 1.0 Release Design

## Objective

Graduate the four published Najm packages from `0.3.0-beta.0` through a coordinated `1.0.0-rc.0` hardening release to `1.0.0`. The release establishes the public compatibility promise described by RFC-0018 and uses objective engineering evidence rather than a fixed waiting period.

The release includes:

- `@monsef-nbj/najm`
- `@monsef-nbj/najm-compiler`
- `@monsef-nbj/najm-router`
- `@monsef-nbj/najm-server`

The repository CLI and `create-najm-app` remain deferred. Their absence does not block `1.0.0` and must remain explicit in user documentation.

## Release Model

Changesets remains the version authority. The four packages stay in one fixed group and always receive the same version.

The existing `beta` prerelease state is closed. A coordinated major Changeset establishes the `1.0.0` line, then Changesets enters `rc` prerelease mode and generates `1.0.0-rc.0`. The RC publishes under npm's `next` dist-tag. The `latest` tag must not move during hardening.

After every promotion criterion passes, Changesets exits prerelease mode and generates `1.0.0` from the same release code. Version metadata and generated changelogs may differ; runtime, compiler, router, and server behavior must not change between the verified RC release commit and stable promotion. Any behavioral fix requires a new RC and a complete rerun of the evidence gate.

Stable publication uses npm provenance and the `latest` dist-tag. All four packages are verified before GitHub release notes and public documentation announce general availability.

## Public API Contract

The repository will add a machine-readable public API manifest covering the runtime, compiler, router, server, and their declared package subpaths. Each public symbol is classified according to RFC-0018:

- Tier 1: stable; breaking changes require a coordinated major release.
- Tier 2: settling; changes require a coordinated minor release and migration note.
- Tooling entry modules: public package paths whose side effects and purpose are stable, even when they do not expose application-callable symbols.
- Internal-only: explicitly excluded from public entrypoints.

An automated test compares actual package entrypoints and exports with this manifest. It rejects removed symbols, unclassified additions, missing export paths, and internal symbols leaking through public entrypoints. Changes to the manifest require deliberate review alongside RFC and changelog updates.

## RC Evidence Gate

`1.0.0-rc.0` is eligible for stable promotion only when all of the following are true:

1. `npm ci`, all repository tests, TypeScript typechecking, package builds, and documentation checks pass.
2. All four workspaces produce valid tarballs containing only declared distribution files.
3. A clean external consumer installs those tarballs and imports or safely resolves every declared public entrypoint.
4. The public API stability test passes against the classified manifest.
5. `npm run bench` passes against the committed RFC-0014 baseline.
6. Documentation has no stale beta install commands or unsupported stable claims.
7. npm reports all four `1.0.0-rc.0` versions and maps each package's `next` tag to that version.
8. No confirmed Tier 1 regression remains open.

There is no fixed soak duration. Evidence can promote the RC immediately, but no gate may be waived silently.

## Stable Promotion Gate

Stable promotion performs these steps in order:

1. Confirm the RC evidence record and that no behavior commit follows the verified RC commit.
2. Exit Changesets prerelease mode and generate coordinated `1.0.0` manifests and changelogs.
3. Rerun the complete local and CI release gate, including packed-consumer tests and benchmarks.
4. Publish all four packages with provenance under `latest`.
5. Verify registry versions, dist-tags, tarball provenance, and every public entrypoint from registry-installed packages.
6. Create the coordinated Git tag and GitHub release.
7. Update and deploy stable installation documentation.
8. Verify the public documentation and clean synchronized `main` state.

## Publishing and Recovery

The release workflow derives the npm tag from package versions:

- `*-rc.*` publishes with `--tag next`.
- Stable versions publish with the default `latest` tag.
- The obsolete hard-coded `beta` behavior is removed.

Publishing is performed by GitHub Actions with npm trusted credentials and provenance. Local commands may build, pack, and inspect artifacts but do not replace reviewed CI publication.

If publication partially succeeds, automation stops. Maintainers inspect all four registry versions and tags, publish only missing members at the same coordinated version, then rerun registry smoke verification. The process never bumps only part of the fixed group, republishes an immutable version, or moves `latest` until all stable packages are present and verified.

## Documentation and Governance

RFC-0018 is revised to record the automated API contract. RFC-0019 is revised to record the RC channel, evidence-based promotion, stable tag behavior, and continued CLI deferral. Accepted decisions are amended through explicit revision notes rather than silent edits.

During RC hardening, user documentation shows `@next` installation commands and clearly labels the release candidate. Stable documentation switches to untagged package installation only after registry verification. Contributor documentation includes the exact RC, promotion, reconciliation, and rollback procedures.

## Testing Strategy

New release tests follow the existing `node:assert` and `tsx` conventions and are registered in the root suite guard. They cover:

- API manifest completeness and tier classification.
- Package export-map coverage.
- RC/stable release-workflow tag selection.
- Stale prerelease language in stable-facing documentation.
- Packed tarball installation and import behavior in a clean temporary project.
- Fixed-group version consistency.

The final verification chain is:

```bash
npm ci
npm test
npm run typecheck
npm run build:packages
npm run pack:packages
npm run test:packages
npm run bench
npm run docs:check
git diff --check
```

Registry and GitHub checks supplement, rather than replace, this local evidence.

## Success Criteria

The work is complete when all four packages exist at `1.0.0`, their `latest` tags resolve to `1.0.0`, package-consumer smoke tests pass against registry artifacts, the `v1.0.0` GitHub release is published, stable documentation is live, and `main` is clean and synchronized. The CLI remains documented as deferred without being advertised by any package manifest.
